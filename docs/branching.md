# 分支与发布规范

配套:`docs/versioning.md`(版本号本身的规则)。本文件讲**分支怎么走、什么时候能发**。

---

## 一、先讲清楚一件事:这里的「规范」有多少是能强制的

GitHub 分支保护在本仓库**用不了** —— 私有仓 + Free 套餐,`branches/master/protection`
返回 403(要 Pro)。所以任何写成「开一下 required status checks」的建议都是**不能执行的**。

于是规范分成两类,**混在一起讲就会误判**��

| 类别 | 靠什么 | 能不能被绕过 |
| --- | --- | --- |
| **闸门** | `tools/release/gate.sh` 的退出码 | 不能。它在 CI 里跑,红了流水线就红 |
| **约定** | 本文档,靠记性 | 能。`--no-verify`、忘记跑、说服自己「这次例外」 |

**本文件里每条约定都尽量配一个能查的判据**,并注明它属于哪一类。
没有判据的句子读起来像规则,其实只是建议 —— 这里明确标出来。

### 为什么「CI 是绿的」不算数

2026-10-05 实测:GitHub Actions 在私有仓超额度时,让 job **一个 step 都不执行**就失败:

```
The job was not started because recent account payments have failed
```

耗时 2 秒,`conclusion: failure`,**零检查**。徽章是红的,看起来像「测试挂了」,
实际是「什么都没发生」。

这是 **fail-open**:它制造了有闸门的错觉,比没有闸门更危险,因为人会因此放心。
所以判定依据只能是**闸门脚本的退出码**,不是任何 run 的状态。

## 二、分支模型:主干唯一,分支一次性

```
master ──●──●──●──●──●──●──●──●  ← 唯一长命分支,随时可发
          ╲              ╱
           ●──●──●──●──●          ← 短期分支,不回来
```

**master 是唯一长命分支。** 其余分支用完即删,不允许活过一天。

### 为什么不搞 PR 评审

私有仓 Free 套餐**没有分支保护**,而没有分支保护时,PR 合并是**无检查的合并** ——
`gh pr merge --admin` 或者网页上直接点合并都能过。此时 PR 只剩下「多一步点按钮」,
却让人**以为**有评审。这是又一处 fail-open,比直接推更糟。

所以:**直接推 master,评审靠人。** 代价是没人拦你,收益是不存在假的绿灯。

真需要隔离时(改动大、想先看看跑不跑得通),开一个短期分支,自己合回去。

### 短期分支的规矩

1. 从 master 切出,合并回去后**立刻删**。
2. **不在分支上改版本号。** 版本号只在 master 的发版 commit 里改(见下节)。
3. 分支上过了闸门不代表能合 —— 合之前 master 可能已经动了,rebase 后重跑。

### 没做而应该明说的

- 没有 pre-push hook。装一个很容易,但 `--no-verify` 能绕过,于是它只是**提醒**。
  真要在本地拦,该靠 `tools/release/gate.sh` 在提交前手动跑。
- 没有 `concurrency`,多条流水线会同时抢 runner(2026-10-05 一天跑了 26 条)。
  这是**省钱**问题不是正确性问题,账单恢复后值得加。

## 三、版本号只在发版那一个 commit 里改

**规则(闸门可查)**:`app/build.gradle.kts` 的 `versionCode` / `versionName`,
只允许在**发版 commit** 里改。发版 commit 必须是 master 的 tip。

于是恒等式成立:

```
master 的版本号  ==  最新已发布版本的版本号
```

tag 一推,「已发布」变成新版本 —— bump 与 tag 相邻**不是巧合,是构造出来的**。

### 这条规则是从一次真实状态里长出来的

2026-10-05 的现场:`3eac2f1`(一个补埋点、修动画、加 E2E 的功能 commit)
顺手把版本号提到 29 / 0.7.10。于是 master 停在 0.7.10 整整 **14 个 commit**,
而已发布的最新是 0.7.9,**没有对应 tag**。

代价不是历史难看,是两句具体的话都定位不到东西:

- 用户报 bug 说「我用的 0.7.10」—— 这句话指向一个**从不存在的产物**。
- 从 master 编出的包自称 0.7.10,装到真机上设置页也写 0.7.10。

### 判据

`gate.sh` 的「版本号漂移」那一步,比的是**值**:解出 HEAD 与最高 tag
各自的 `build.gradle.kts`,比 `versionCode` + `versionName`。

- 相同 → 正常开发中(master 承袭已发布版本)
- 不同,且 **HEAD 自己**改了这个文件 → 待发版
- 不同,HEAD 没改 → **漂移**,报错并指出漂了几个 commit

> 注意是比**值**,不是「哪个 commit 碰过这个文件」。后者会把「顺手修了个 typo」
> 也算成一次 bump,判据不准 —— 这个错误在实现时真的犯过一次。

### 推论:功能 commit 不许碰版本号

`docs/versioning.md` 早先写的是「改版本号,与改动一起提交」。**本条覆盖它。**
两者不能同时成立 —— 那句是「顺手改」的许可,正是漂移的成因。

## 四、四道闸门,各有各的覆盖面

**别把它们当成一道。** 它们验的东西根本不同,谁也替代不了谁:

| 闸门 | 验什么 | 覆盖不到的 |
| --- | --- | --- |
| **单测** | 纯函数、状态机 | 碰不到 native、碰不到 R8 |
| **JNI 符号** | R8 有没有削掉入口名 | 碰不到交互时序 |
| **E2E** | 打字、选字、翻页时序 | **debug 包不过 R8** ⇒ 碰不到产物 |
| **签名核对** | 能不能覆盖升级 | 碰不到任何功能 |

历史依据:

- 2026-10-04:JNI 闸门抓到已发布的 v0.7.1 里 **14 个入口被 R8 削掉 7 个** ⇒
  真机上拼音引擎整个不可用。而 **E2E 结构上看不到**(它跑 debug 包)。
- 2026-10-05:本地编的包与 CI 编的**不是同一套工具链**(本机 CMake 3.31.10,
  CI 固定 3.22.1),而 `gate.sh` 的预检会把这个差异**说出来**。

### E2E 为什么硬接不进流水线

现状:E2E 与 release 都在 `on: push: tags: ['v*']` 上触发,**并行、无依赖** ——
所以 E2E 红了 release 照样绿。

要接成前置,`needs` 跨不了 workflow,只能重构成 reusable workflow,
代价大且会丢掉 `workflow_dispatch` 入口(素材采集要用)。
而**换来的仍然不是「产物被验过」**,因为 E2E 装的是 debug 包。

所以诚实的做法:**E2E 是发版前的人工前置,不是产物闸门。**
唯一能查的部分是「不许默默跳过」—— `gate.sh --release` 要求发版 commit 里
引用一次 E2E run,或写明为什么不做。

> 这个检查**只在本地推 tag 前跑**,不在 CI 里跑。CI 里查它等于稳定误报
> (tag 推上去时 commit message 早写死了),而会误报的闸门只会被绕过去。

## 五、发版流程

```bash
# 1. 确认工作区干净、闸门绿
git status --short              # 必须无输出
tools/release/gate.sh           # 七步全过

# 2. 跑一次 E2E(它是发版前的人工前置,不是产物闸门)
gh workflow run 'E2E (模拟器)' -f scenes=consume-partial
gh run watch <run-id>

# 3. 发版 commit:唯一改版本号的地方
#    message 里贴上 E2E run 链接 —— 这是「跑过了」的书面证据
git commit -am "v0.7.10:<一句话说清改了什么>"
#    ↑ 版本号改动在这一步(改 app/build.gradle.kts)

tools/release/gate.sh --release   # 查 E2E 引用 + 其余六步

# 4. 打 tag 并推 —— 这一推才真的发版
git tag -a v0.7.10 -m "v0.7.10"
git push origin v0.7.10
```

第 4 步之后:`release.yml` 只在应用仓库建 release,不再同步到公开站点。
**站点从 2026-10-23 起只发测试版 β 与开发版 dev**,正式版不占站点位置 ——
原来的 `publish-site` job 与 `sync-apk-to-site.sh` 已删除。

### 为什么 tag 是「发布动作」

推 tag 之前,代码可以随便改 —— 没人看得到。
推 tag 之后,就有了必须对齐的东西:`tag` 与 `versionName`(以及 Release 标题/资产名)。
`check-version.sh` 守的就是这个对齐。

## 六、什么算 breaking(升 minor)

`0.x` 时代 **minor 位就是 breaking 的信号**。判据不是「改动大不大」,
而是**用户手上的东西会不会失效**:

| 判据 | 升什么 |
| --- | --- |
| 手感/动画引擎换了、档位口径变了、状态语义变了 | **minor** |
| 只加功能、只修 bug、只改文案 | patch |

**别为了「看起来改动多」而升 minor** —— 那会让 minor 失去信号,
下次真 breaking 时用户不再当回事。

`versionCode` 只增不减,与 minor/patch 无关,它是发布次数的计数器。

## 七、待办(都是约定,没有判据)

这些是**约定**,没有脚本查得了,所以明说:

1. **没有分支保护**,所以「master 随时可发」靠人保证。至少每次推之前跑一次闸门。
2. **没有 `concurrency`**,26 条流水线会互相抢 runner。账单恢复后加。
3. **E2E 引用靠 commit message**,可以被人随手写个假链接骗过。
   真要硬保证,得让发版 commit 由脚本生成。
4. **本地与 CI 工具链可能不同**(本机 CMake 3.31.10 / CI 3.22.1)。
   `gate.sh` 会提示,但拦不住 —— 拦得住的只有「产物必须由 CI 出」。
